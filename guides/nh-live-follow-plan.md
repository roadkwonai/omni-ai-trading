# 실계좌 모의 전략 추종 실행기 설계 (`nh_live_follow`)

작성: 2026-11-12 (Asia/Seoul). 상태: **구현 완료, 기본 꺼짐(dry-run), launchd 미등록.** 실주문을 켜는 것은 사용자의 별도 승인 사항이다.

## 1. 목적과 구조 (2026-11-12 미러 방식으로 변경)

모의 실행기(`nh_paper_isolated.py`, 공유 모의계좌)와 **같은 전략을 실계좌에서 그대로** 운용한다. 실계좌 실행기는 전략을 따로 계산하지 않고, 모의 실행기가 실제로 체결한 원장(`shared-etf-paper/orders.sqlite3`의 `fills`, 모의 실행기가 스스로 보유를 판단하는 그 원장)을 읽기 전용으로 따라간다.

```
모의 실행기 (Jev 판단 · 학습 필터 · 관심종목 강도 · 국면별 청산 · 종가매매 · 다일 스윙 · 저장된 매매 기준)
        │ 실제 주문 · 체결 대조
        ▼
shared-etf-paper/orders.sqlite3 fills ──> paper_book ──> mirror_target (모의 분할 매수 1회 = 실계좌 1주)
                                                              │
NH 읽기 전용 조회(잔고·주문·손익·호가) ──────────> decide (실계좌 승인 한도만 추가)
                                                              │
                         nh_guarded_live.execute ─> LiveOrderGuard ─> 전송 ─> 다음 주기 체결·잔량 대조
```

그래서 모의 쪽 전략·설정·학습 데이터가 보완되면 그 결과(모의 체결)가 다음 주기부터 실계좌에도 그대로 반영된다. 실계좌 쪽에 전략 코드나 설정을 따로 옮길 필요가 없다.

### 전에 차이가 컸던 이유

이전 실행기는 `nh_live_shadow.account_shadow`(가상 실행)를 목표로 삼았다. 가상 실행은 모의 실행기의 기록(진입 통과, 청산 계획, 1분봉 종가)으로 전략을 **다시 계산한 별도 구현**이라 다음이 어긋났다.

| 차이 | 가상 실행(이전) | 미러(현재) |
|---|---|---|
| 판단 근거 | 진입 통과 기록 + 1분봉 종가로 재계산 | 모의 실제 체결 |
| 분할 추가 매수 | 진입 통과 1건 = 1주, 모의 분할 규칙과 다름 | 모의 분할 1회 = 1주 |
| 부분·전량 익절, 손절, Jev/vibe 매도 | 기록으로 재현(시각·가격 다름) | 모의가 판 만큼 판다 |
| 모의 주문 가드가 막은 진입 | 가상으로는 삼 | 체결이 없으니 안 삼 |
| 장중 기준 변경 | 하루 전체를 다시 계산해 과거 판단이 바뀜 | 이미 체결된 사실은 안 바뀜 |
| 실계좌 2(vibe 엔진) | vibe 점수로 별도 재계산 | vibe 모의 실행기 원장을 따름 (지금은 원장 없음, 아래) |

2026-11-12 예: 모의는 삼성전자 10:54 4주 + 12:38 4주 = 8주를 보유했지만, 가상 실행은 실계좌 1 삼성전자 1주, 실계좌 2 251340 2주 + 삼성전자 1주였다. 미러 목표는 실계좌 1 삼성전자 2주다.

가상 실행 카드(`account_shadow`)는 대시보드 관찰용으로 남겨 두었고 실주문에는 쓰지 않는다.

### 그래도 남는 차이 (승인된 실계좌 한도 때문)

- 크기: 모의 분할 1회(약 100만 원)가 실계좌 1주다. 손익 크기는 다르고 방향·시점만 같다.
- 계좌 1주 가격 상한을 넘는 종목, 운용금 100만 원을 넘는 추가 매수, 하루 신규 6번째 종목은 사지 않는다.
- 하루 손실 2만 원 래치(모의는 30만 원)와 실계좌 매수평균가 대비 손절 %(최대 2%)는 실계좌에만 있다. 걸리면 모의보다 먼저 판다.
- 시점: 모의 체결이 원장에 기록된 뒤 다음 주기(최대 1분)에 따라간다. 그사이 매수호가가 모의 체결가보다 0.3%(`CHASE_LIMIT`) 넘게 오르면 따라 사지 않고 기다린다. 전날 이전에 시작된 모의 매수는 따라 사지 않는다.
- 메인 엔진별 원장 (`paper_source`): 실계좌는 자기 메인 엔진으로 매매하는 모의 실행기의 원장을 따른다. 사용자 운용 계획(2026-11-12)은 실계좌 1 = Jev, 실계좌 2 = vibe다.
  - 공유 모의 실행기(`paper-shared`) 엔진과 같으면 `shared-etf-paper/orders.sqlite3` (지금 Jev → 실계좌 1)
  - vibe는 vibe 모의 실행기(`vibe_runner.py`) 원장 `vibe-paper/orders.sqlite3` (실계좌 2)
  - 원장이 없으면 새로 사지 않고, 이미 산 것은 실계좌 손절·손실 래치로만 관리한다.
- **실계좌 2(vibe)는 가상 체결 원장을 따른다 (2026-11-12 사용자 결정 "가상 체결로 운용").** 국내주식 모의계좌가 공유 계좌 하나뿐이라(분리 모의계좌는 상품코드가 주식 01이 아님), vibe 모의 실행기(`vibe_runner.py --virtual`, launchd `com.vibetrading.vibe-paper`, 평일 09:11~15:00)가 `virtual_paper_broker.VirtualBroker`로 돈다. 실행기 코드·한도는 그대로이고 체결만 실시간 호가로 가상 기록한다(매수는 매도호가, 매도는 매수호가에 전량, 호가에 닿지 않으면 대기 후 취소, 수수료·세금·부분 체결 없음). 가상 계좌 1,000만 원(`vibe-paper/virtual-account.sqlite3`).

## 2. 가드 일반화 (`agent/src/tools/nhplug_live_guard.py`)

`LiveOrderGuard(account, root, symbols=('114800',))`: 만들 때 받은 종목만 주문할 수 있다. 기본값은 114800 하나라서 기존 경로(`nh_live_auto`, `nh_guarded_live` CLI, `nhplug_live_execution`)의 동작은 바뀌지 않는다.

| 항목 | 범위 | 변경 |
|---|---|---|
| 보유 원장 `_owned` / `owned(symbol)` | 종목별 | 매수·매도 체결과 인계를 종목으로 나눠 센다 (전에는 매수 합계가 종목 구분 없었음) |
| 기존 보유 인계 `adopt_existing(symbol=)` | 종목별 | 잔고·매도 가능 수량을 그 종목으로 확인 |
| 미체결 주문 인계 `adopt_order` | 허용 종목 | 주문의 종목을 그대로 기록 |
| 매도 가능 수량·잔고 대조 | 종목별 | 원장 보유 ≥ 1, 증권사 잔고 ≥ 1, 매도 가능 수량 조회 종목 일치 |
| 매도 취소 후 대체 매도 | 종목별 | 다른 종목의 취소 매도가 이 종목 매도를 막거나 대체하지 않음 |
| 호가 종목 확인 | 주문 종목 | 다른 종목 호가로는 매수 불가 |
| 취소 요청 | 주문 종목 | 미체결 원주문과 종목까지 같아야 함 (더 엄격해짐) |
| 하루 손실 2만 원 래치 | 계좌 전체 | 변경 없음 |
| 운용금 100만 원 (`tot_byn_amt + 가격`) | 계좌 전체 | 변경 없음 |
| 1회 1주, KRX 현금 지정가 | 주문마다 | 변경 없음 |
| 1주 가격 상한 200만 원(가드) | 매수·매도 | 변경 없음 |
| 계좌 설정 1주 가격 상한(`live_price_cap`) | 매수만 | 2026-11-12 사용자 승인: 매도는 제외 (아래 4.4) |
| 매도 지정가 하한 | 매도 | 신규: 같은 종목 현재 매수호가보다 3%(`SELL_FLOOR_PCT`) 넘게 낮으면 거부 |
| 미체결·미확인 주문이 있으면 모든 종목 신규 주문 차단 | 계좌 전체 | 변경 없음 |
| 하루 신규 5종목 (`DAILY_NEW_SYMBOLS`) | 계좌 전체 | 2026-11-12 사용자 승인: 하루 매수 1회를 없애고 모의 주문 가드와 같은 기준으로 바꿈. 그날 이미 산 종목의 재매수는 세지 않고, 전송 전 중단이 증명된 매수도 세지 않음 |
| HALT, 매수 일시중지(`LIVE_BUY_PAUSED`) | 계좌 전체 | 변경 없음 |

`nh_live_broker.collect_snapshots(..., symbol=)`가 주문 종목 호가를 읽고, `nh_guarded_live._execute`는 `fields['iem_cd']`가 가드 허용 종목인지 확인한 뒤 그 종목의 매도 가능 수량과 호가를 읽는다.

## 3. 실행기 동작 (`scripts/nh_live_follow.py`)

1분마다 한 주기:

1. 장 시간 확인: 주말·15:20 이후 STOP, 09:00 전 WAIT.
2. 그 원장의 `fills`를 읽기 전용으로 읽어 종목별 보유와 "이번 보유가 시작된 뒤의 분할 매수 횟수·매수 수량"을 구한다(`paper_book`).
3. 목표 = 반올림(모의 보유 × 분할 횟수 ÷ 분할 매수 수량), 모의가 1주라도 들고 있으면 최소 1주(`mirror_target`). 예: 4주씩 두 번(8주) → 2주, 절반 익절 후 4주 → 1주, 전량 매도 → 0주.
4. 계좌 엔진의 모의 원장을 고른다(`paper_source`). 원장이 없으면 목표 = 현재 보유(새 매수 없음)로 두고 `no paper ledger for engine …` 경고를 기록한다.
5. 가드는 ETF 7종 + 목표 종목 + 원장에 있던 종목으로 만든다. NH 읽기 전용 조회(계좌·당일 주문·잔고·손익)로 하루 손실 래치를 갱신한다.
6. 이 실행기 원장에 미체결·미확인 주문이 있으면 체결·잔량을 대조하고, 접수 후 60초가 지나도 남은 주문은 취소한다(실주문 모드만). 이 주기에는 새 주문을 내지 않는다.
7. 보유 종목마다 증권사 매수평균가(`phs_pr`, 문자열도 허용) 대비 손절 %(계좌 규칙, 최대 2%)를 호가로 확인한다. 걸리면 그날 그 종목을 청산 대상으로 고정(`follow_exits`)한다.
8. 살 수 있는 종목: 목표 > 보유, 모의가 그 종목을 **오늘** 샀고, 지금 매도호가 ≤ 모의 마지막 체결가 × 1.003.
9. `decide` 순서:
   - 원장 미체결 → RECONCILE
   - 이 실행기가 내지 않은 증권사 미체결 → BLOCK (사용자 주문을 건드리지 않음)
   - 원장 보유 > 증권사 잔고 → BLOCK (사람이 대조)
   - 하루 손실 래치면 목표를 모두 0, 손절 고정 종목도 0
   - 원장 보유 > 목표인 종목을 1주 매도 (매도가 매수보다 먼저)
   - 목표 > 보유이고 살 수 있는 종목이며 09:10~14:30, 매수 일시중지가 아니면 1주 매수
10. 주문가는 매수 시 매도호가(ask), 매도 시 매수호가(bid)인 지정가 1주다. 주문은 `nh_guarded_live.execute`만 거친다.
11. 기록: `~/.vibe-trading/nhplug/live-follow.jsonl` (계좌 키만 기록, 계좌번호 없음). `paper`(모의 보유), `target`, `owned`, `held`, `loss`, `halted`, `warning`과 `mode`(`dry_run`/`execute`), `execution`(`DRY_RUN` / `NO_ORDER` / `BLOCKED` / `ACKNOWLEDGED_NOT_FILLED` / `CANCEL_ACKNOWLEDGED_NOT_RECONCILED`).

사용자가 직접 산 종목(원장에 없는 보유)은 팔지 않는다. 설정(`accounts.json`)은 매 주기 다시 읽고, 자동매매를 끄면 그 주기부터 계획만 기록한다.

실행 예 (읽기 전용 조회만, 주문 없음):

```bash
cd scripts && PYTHONPATH=../agent:. ../.venv/bin/python nh_live_follow.py --account live-1 --once
```

## 4. 위험

1. **NH API 호출 한도.** 2026-11-12 12:25 dry-run 두 번이 `IGW42902`(호출 건수 초과)로 막혔고, 같은 시각 모의 실행기도 분봉 조회 한 번(`market_bars_unavailable`)을 건너뛰었다. 앱 키를 모의 실행기·대시보드·vibe·시장 수집기와 함께 쓴다. 이 실행기는 한 주기에 조회 6건 이상(+보유 종목당 호가 1건, 주문 시 `collect_snapshots` 한 번 더)을 쓴다. 한도에 걸리면 주문하지 않고 BLOCK으로 남지만, **그동안 손절 매도도 못 한다.**
2. **체결가 차이.** 실계좌는 모의 체결 뒤(최대 1분) 그때 호가로 주문한다. 매수는 모의 체결가 +0.3% 안에서만 따라가지만 매도는 가격과 상관없이 따라간다. 수수료·세금·스프레드 때문에 실계좌 손익률은 모의와 다르다. 대시보드 가상 실행 카드는 이전 재계산 방식이라 실주문과 다를 수 있다.
3. **매수 횟수 (2026-11-12 해결).** 하루 매수 1회 제한을 없애고 모의 주문 가드(`nhplug_order_guard`)와 같은 "하루 신규 5종목"으로 바꿨다. 모의의 금액 한도(회당 300만·하루 600만 원)는 실계좌 운용금 100만 원보다 커서 옮기지 않았고, 1회 1주·계좌 가격 상한·운용금이 그 역할을 한다. 매매가 잦아지면 수수료·스프레드가 늘지만 수수료는 하루 손실 계산(`sdr_xps`)에 들어가 2만 원 래치가 막는다. 진입 시간(14:30)과 연속 손실 쉼은 모의 진입 기록을 따라가므로 이미 반영된다. 미러 방식에서는 모의 체결만 따르므로 모의 가드가 막은 진입은 실계좌도 사지 않는다.
4. **매도 가격 상한 (2026-11-12 해결).** 전에는 `nh_guarded_live._execute`와 `nh_live_auto`가 매도에도 계좌 1주 가격 상한을 걸어, 산 뒤 상한을 넘게 오른 종목이나 상한을 낮춘 뒤의 보유분을 손절·익절·손실 래치로도 팔 수 없었다. 매도는 보유를 줄일 뿐이고 위쪽 한계는 싸게 파는 실수를 막지 못하므로, 계좌 상한은 매수에만 적용한다. 대신 매도에는 같은 종목 현재 매수호가 대비 3% 하한을 새로 걸었다. 가드의 1주 최대 200만 원은 매도에도 그대로라, 200만 원을 넘게 오른 종목은 여전히 자동 매도가 막힌다(운용금 100만 원이라 두 배 이상 올라야 해당). 3% 하한은 주문 직전 다시 읽은 매수호가로 판단하므로, 몇 초 사이 3% 넘게 급락하면 그 주기 매도가 거부되고 다음 주기(1분 뒤) 새 호가로 다시 시도한다.
5. **모의 원장에 의존.** 모의 원장(`orders.sqlite3`)이 손상되거나 모의 실행기가 멈추면 실계좌도 새 매매를 하지 않는다. 원장을 읽지 못하면 그 주기는 BLOCK이고, 그동안 실계좌 손절·손실 래치 매도도 함께 멈춘다. 모의에서 사람이 직접 낸 주문(수동 매도 등)도 체결되면 실계좌가 따라간다.
6. **종가매매·다일 스윙.** 모의 실행기가 다음 날까지 보유하면 실계좌도 보유한다. 밤사이 갭 손실은 손절 %를 넘을 수 있다. 하루 손실 2만 원은 보수적 추정치이고 체결을 보장하지 않는다.
7. **원장과 증권사 잔고 불일치.** 사용자가 이 실행기가 산 주식을 직접 팔면 원장 보유 > 잔고가 되어 실행기 전체가 BLOCK된다. 직접 대조 후 원장을 정리해야 한다(기록 삭제 금지, 정리 절차는 별도 승인).
8. **실주문 계좌 제한.** `--execute`는 `.env`의 `ACCOUNT_NUMBER`와 같은 계좌에만 허용한다(주문 인증 정보가 그 계좌 것이라서). 다른 실계좌는 dry-run만 된다.
9. **live-auto와 동시 실행 금지.** 실주문 모드는 `live-auto.lock`을 함께 잡는다. 같은 원장(`live-orders.sqlite3`)과 하루 신규 5종목 한도를 공유한다.
