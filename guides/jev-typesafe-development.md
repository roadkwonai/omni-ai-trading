# Jev 개발·장애 대응 가이드

Jev 요청, 판단 입력, 장애 복구, 호출 비용이나 지연을 바꿀 때 이 가이드를 사용한다. 종목별 프로그램 수급과 추세형 청산을 재현하려면 [격리 모의 검증 가이드](jev-program-paper.md)를 따른다.

## 변경 범위를 확인한다

- [Jev 주 호출](../scripts/nh_etf_auto_v2.py)은 차트, 시황과 판단 질문을 전송하고 응답을 검증한다. [관심종목 선정](../scripts/watchlist.py), [별도 호출](../scripts/nh_jev_compare.py), [이벤트 판단](../scripts/vibe_event_jev.py)에도 변경이 닿는지 확인한다.
- [모의 실행기](../scripts/nh_paper_isolated.py)는 판단과 시세의 유효시간, 주문 조건과 위험 규칙을 적용한다. 실계좌 미러와 주문 원장에 영향을 주는 변경은 격리 모의에서 먼저 검증한다. 데이터나 응답이 유효하지 않으면 해당 모델 신호를 보류하고 손절·청산 감시는 기존 위험 규칙으로 계속한다.
- 모델 버전은 [설정 코드](../scripts/paper_ai_modes.py)에서 `jev-1.14.0`으로 고정한다. 변경 시 응답의 실제 모델 버전과 판단 결과를 비교한다. 별칭은 같은 코드에서도 뒷단 모델이 바뀔 수 있다. [TypeSafe 모델 가이드](https://docs.typesafe.ai/models#aliases)

## 요청을 검증하고 오류를 분류한다

요청은 UTF-8 JSON이며, 본문 최대 32 MiB, `state`·질문 지시·선택지 각각 최대 64단계 중첩을 기준으로 검사한다. 비유한 수치는 결측으로 처리한다. 빈 값과 0의 의미를 구분한다. 차트는 실제 출력 파일의 폭과 높이, 형식과 참조를 확인한다. 공식 규격의 폭·높이는 각각 280~1568픽셀이며 이미지 기능 헤더가 필요하다. 이 규격은 개발 시 공식 문서에서 다시 확인한다. [요청 규격](https://docs.typesafe.ai/api/errors#request-rules) · [이미지 규격](https://docs.typesafe.ai/images#limits)

| 증상 | 조사·대응 기준 |
| --- | --- |
| `400`, `413`, `415`, `422` | JSON·깊이·본문 크기·인코딩·질문 구조·이미지를 확인한다. `max_tokens_exceeded`가 확인되면 중복 데이터와 선택에 필요 없는 장문부터 줄인다. 같은 요청을 즉시 반복하지 않는다. |
| `401` | 키 사용 여부와 인증 설정을 점검한다. 키 값은 출력하지 않는다. |
| `429`, `529` 또는 일시적 연결 실패 | 제공처 대기 안내를 확인한다. 지수 백오프와 작은 무작위 지연을 적용할 때는 전체 판단 유효시간과 호출 잠금 시간을 먼저 제한한다. 남은 시간이 부족하면 다음 회차에 새 시세로 판단한다. |
| 응답 구조 오류·판단 지연 | 모델·질문·옵션·신뢰도 범위와 응답 시각을 확인한다. 오래되거나 검증되지 않은 응답은 주문 근거로 쓰지 않는다. |

재시도는 TypeSafe 판단 요청의 범위다. 주문 제출을 다시 실행하는 조건으로 사용하지 않는다. 같은 회차에서 정규 판단과 이벤트 판단이 공유 잠금을 어떻게 사용하는지도 확인한다. [오류 대응](https://docs.typesafe.ai/api/errors#handling-rate-limits) · [SDK 재시도 정책](https://docs.typesafe.ai/sdk/python/api/retries)

주 호출 코드는 비유한 수치를 `null`로 보내고 차트 DPI를 고정한다. 전송 전에 JSON과 PNG 규격을 검사한다. 감사 DB의 `snapshots`에는 HTTP 오류를 `jev_http_error`, 전송 전 검증 실패를 `jev_request_rejected`로 남긴다. HTTP 오류 이력에는 시각, 상태 코드, 오류 분류, 제공된 요청 ID, 요청과 이미지 크기, 질문 수, 필드별 바이트와 해시가 들어간다. 요청·응답 원문과 인증키는 오류 이력에서 제외한다. 정규 Jev 주 호출의 코드 변경과 실행 중인 프로세스의 반영 여부는 구분한다. 재시도와 다른 호출 경로의 진단 통합은 별도 검증 대상이다. [주 호출 코드](../scripts/nh_etf_auto_v2.py) · [공통 요청 검사](../scripts/jev_request.py)

## 장애 원인을 추적한다

1. KST 기준 첫 오류·마지막 오류·첫 정상 응답 시각을 확인한다. HTTP 실패 건수는 API 이력으로, 진입 또는 보유 판단 보류는 실행기 원장으로 대조한다. 청산 주문의 접수와 체결은 따로 확인한다.
2. [장중 감사 절차](../.agents/skills/intraday-audit/SKILL.md)에 맞춰 호출 유형, 상태·오류 분류, 요청 ID, 이미지 크기와 필드 크기를 읽는다. 최근 시세, 정상 판단 또는 기존 위험 규칙이 계속 동작했는지 함께 확인한다.
3. 당시 실패에서 확보한 증거와 나중에 만든 재현을 구분한다. 2026-11-26 오전 TypeSafe HTTP 400 19건은 실패 원문이 없어 원인 미확인이다. 별도 시험에서 `NaN` 요청 400과 `null` 요청 200을 확인했다.
4. 주문과 분리된 환경에서 재현하고 변경 전후 결과를 기록한다. 반복 장애와 복구를 각각 한 번 알려준다. 실행 환경에서 실제 반영 여부를 별도로 확인한다.

감사 DB의 최신 HTTP 오류를 읽는다.

```sh
scripts/ro sql ~/.vibe-trading/nhplug/shared-etf-paper/market-research.sqlite3 \
  "SELECT time, payload FROM snapshots WHERE kind='jev_http_error' ORDER BY id DESC LIMIT 10"
```

## 입력을 줄이고 판단 품질을 비교한다

1. 먼저 호출 유형·후보 수·모델 버전·실제 `usage.input_tokens`·요청 바이트·이미지 크기를 기록한다. 차트 생성, API 응답, 전체 판단 시간을 따로 재고 중앙값과 95백분위, 오류율을 남긴다. JSON 크기로 실제 토큰 또는 비용을 추정하지 않는다.
2. 장전 자료와 매매일지에서 현재 질문에 필요한 항목만 고른다. 진입에는 후보별 뉴스·공시, 시황과 수급을 남긴다. 보유 판단에는 보유 종목의 최신 변화와 청산 계획을 우선한다. 정적 요약을 로컬에서 재사용하더라도 요청이 같으면 토큰 절감으로 집계하지 않는다.
3. 기존 차트, 핵심 종목만 담은 차트, 이미지 없이 수치만 보낸 요청을 각각 실험한다. 수익률·VWAP·거래대금 변화·시세 신선도는 코드가 계산한다. Jev는 뉴스와 가격 움직임의 관계처럼 해석이 필요한 질문을 맡는다. 관련 질문은 같은 요청에서 평가하고 쓰임을 확인하기 전 보조 질문을 제거하지 않는다. [모델 한계](https://docs.typesafe.ai/model-jaggedness) · [이미지 토큰](https://docs.typesafe.ai/images#image-tokens) · [다중 질문](https://docs.typesafe.ai/patterns/fan-out)
4. 같은 종목과 시점의 원본 요청·변경 요청을 짝지어 비교한다. 유효 진입 누락, 불필요한 조기청산, 판단 불일치, 비용 반영 손익과 자료 누락을 확인한다. 실험당 한 가지를 바꾼다. 후보 수에 따른 신뢰도와 선택 확률·2위와의 격차는 별도로 검증한다. 모델 선택 확률은 실거래 수익 확률로 쓰지 않는다. [TypeSafe 신뢰도](https://docs.typesafe.ai/confidence#when-to-act-on-confidence)

검수 기록에 적용 위치, 동일 입력의 전후 비교, 오류 시 동작, 주문 경로 영향과 미검증 항목을 남긴다. 관련 회귀 테스트는 `test_jev_http_diagnostics.py`, `test_nh_etf_auto_v2.py`, `test_watchlist.py`, `test_jev_activity.py`에서 대상에 맞게 선택한다.

정규 Jev 성공 응답의 `model_inputs.response.request_metrics`에는 제공처 입력 토큰, 요청·이미지 크기, 차트 생성과 API 구간, 함수 시작부터 응답 검증까지의 시간이 들어간다. 토큰을 제공하지 않은 응답은 미측정으로 남는다. 정상 HTTP 응답의 JSON 또는 판단값이 잘못되면 `jev_response_rejected`로 따로 기록한다. 제공된 확률은 합이 약 1이어야 하고 선택값은 최댓값에 해당해야 한다. 연결 실패와 타임아웃은 `jev_transport_error`로 기록한다. 아래 명령의 HTTP 오류 비율은 측정된 성공·HTTP 오류·응답 검증 실패·연결 실패를 분모로 사용한다. 이전 원장과 전송 전 거절은 구분해 표시한다. 전체 운영 장애율은 기존 API·실행기 감사와 대조한다.

```sh
scripts/ro jev_explain.py --metrics --since 2026-11-26T09:00:00+09:00
```

`model_inputs.inputs`의 JSON을 로컬 파일로 내보낸 뒤, 다음 명령으로 장전 자료와 매매일지 축소 전후의 구조화 입력 바이트를 비교한다. 이 비교에는 이미지와 보조 질문이 포함되지 않는다.

```sh
PYTHONPATH=agent:scripts .venv/bin/python scripts/jev_input_compare.py capture.json --question candidate
```

장외 모델 비교에는 `--ask-jev --chart chart.png`를 붙인다. 저장된 질문 ID와 모델 버전을 사용한다. 이전 원장에 이 값이 없으면 `--question`과 `--model`을 명시한다. 원본 PNG는 저장된 해시와 확인한다. 같은 대체 차트를 양쪽에 넣어 비교하려면 `--paired-chart chart.png`를 명시한다. 대체 차트는 원본 재현으로 분류하지 않는다. 두 호출은 매매 주문과 분리되며, 주 질문의 선택·신뢰도와 실제 입력 토큰을 비교한다. 두 번째 요청이 실패하면 첫 번째 결과와 실패한 요청 구분을 함께 남긴다. 각 요청은 한 번만 실행한다. 보조 질문을 포함한 전체 운영 요청의 품질, 응답 변동성, 체결 성과와 거래 비용은 단일 비교로 검증되지 않는다.

## 관심종목 강도 진입을 재현한다

`strength_review_trial_on`은 기본 꺼짐이며, 켜도 주문을 보내지 않는 ETF7 모의 회차에서만 적용한다. 관심종목 순위는 검토 대상을 고르는 자료다. 시험 규칙은 최신 Jev가 `WAIT`이거나 다른 종목을 골랐으면 강도 진입을 보류한다. 종목 소속 시장의 장중 흐름, 시장·종목 뉴스, 당일 투자자 수급, 주문 호가의 시가·최근 저가·판단가 대비 위치도 따로 확인한다. 수급의 `investor_read_at`은 조회 시각이며 공급자가 값을 집계한 시각은 아니다. 과거 시각 정보가 없으면 미확인으로 분류한다. 수급이 부족한 경우 시장 전체 프로그램 수급으로 대신 채우지 않는다.

```sh
PYTHONPATH=agent:scripts .venv/bin/python scripts/strength_entry_replay.py --day 2026-11-26
```

재현기는 새 주문이나 추가 모델 요청을 내지 않는다. 제출 당시 게이트 직전 15초 안의 Jev 진입 판단을 시각으로 대조한다. 기존 주문·체결은 원장으로 확인하되, 보류했을 때 대신 들어갔을 거래와 거래 비용은 계산하지 않는다. 2026-11-26 기록에서는 미래에셋벤처투자·삼성전자뿐 아니라 수익 거래인 나노신소재도 엄격한 `WAIT` 보류 조건에 걸렸다. 실제 적용은 동일 기간의 이익·손실 거래를 모두 비교해 판단한다.
